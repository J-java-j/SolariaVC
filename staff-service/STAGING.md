# Private staging for the Solaria Team Portal

The default website build serves the current launcher at `/staff`. The authenticated portal is a build-time opt-in. The mock role switcher and local outbox are development tools. Solaria Sign and both Terminal entries continue to authenticate their own users.

## Configure an isolated environment

1. Within the approved Solaria project, reserve three separate Cloud Run services named `solaria-team-staging-web`, `solaria-team-staging-terminal`, and `solaria-team-staging-verifier`. Use their HTTPS service origins, dedicated staging runtime identities, test secrets, a staging Identity Platform tenant (display name starting with `staging`), and a named Firestore Native database such as `team-login-staging`. Enable tenant email/password. Deny client SDK access to the session database. Scope server database IAM to the staging database. Set TTL on the `expires` field for `teamBrowserSessions`, `terminalTickets` and `terminalSessions`. Each lookup enforces expiry independently. Stop if creating a tenant requires changing the live project's authentication configuration without separate authorization.
2. Build the website Dockerfile with `VITE_TEAM_PORTAL_ENABLED=true`, a staging web API key restricted to the staging identity workflow, and the staging `VITE_TEAM_FIREBASE_TENANT`. The website image includes the embedded staff API and its locked dependencies. Supply the matching runtime values from [staging.env.example](staging.env.example). Limit the website pilot to one instance while account mutations use an in-process queue. Configure Sign with `SIGN_STORE=local`, `SIGN_DATA_DIR=/tmp/staging-sign`, and `SIGN_BASE_URL` equal to the staging website for this login-only pilot. Give its service account no access to live Sign storage. Use separate mail credentials and a test recipient allowlist.
3. Run the verifier from the same image with command `node staff-service/verifier.js` and Cloud Run authentication required. Configure its project, tenant, session database, verifier origin and exact staging Terminal caller email. Grant that Terminal runtime account Cloud Run Invoker on this verifier only. The Terminal image requires `TEAM_PORTAL_ORIGIN`, `TEAM_VERIFIER_ORIGIN`, and `TERMINAL_PUBLIC_URL` set to the staging origins. Terminal obtains its audience-bound ID token from the metadata server. Provide a staging-only admin password file, a staging-owned shared writable access/settings volume, and separate market configuration. For login testing, use an inert market key and block outbound market calls while allowing the metadata server and verifier. Do not mount the production Terminal password file, bucket, or secret.
4. Verify a staging sender domain with Resend. Configure `TEAM_MAIL_FROM` and inject `TEAM_RESEND_API_KEY` from the secret store. Disable click tracking for password-setup links. Restrict recipients to the approved pilot list. The API generates a Firebase one-time password action code and sends a **Set your password** link to the configured portal origin. Its fragment carries the code to the browser. Delivery failure leaves the new account available for an authorized invitation retry. Pending, active accounts can receive a new invitation. [Firebase action links](https://firebase.google.com/docs/auth/admin/email-action-links) · [Resend email API](https://resend.com/docs/api-reference/emails/send-email)

## First Owner

A designated Firebase operator independently confirms the approved email and project with the organization, authenticates using the staging operator identity, and sets `TEAM_OWNER_EMAIL` in that operator environment. The public website and management API cannot create Owners. With the configuration above loaded, run from the repository root:

```powershell
npm.cmd --prefix staff-service run setup:owner -- --project <confirmed-staging-project-id> --email <approved-owner-email>
```

The command compares both inputs with the configured environment, reads the project's existing accounts, and reserves a fixed UID when creating the first Owner. It resumes an incomplete reservation for the same address. A pending Owner can get a fresh invitation on rerun. An Owner with a password keeps their identity and credential. A conflicting Owner causes the command to stop. Keep the command result and operator identity in the staging change record, with no action codes or tokens.

The Owner opens the email, sets and confirms their password, signs in through the shared Team login form, and invites the first Board Admin from **Board Admins**. For a fully local rehearsal run `npm.cmd --prefix staff-service test`. The suite starts an empty second emulator and exercises the operator command, first password, first sign-in, first Board Admin invitation, rerun, and conflicting target. It preserves the review emulator on 9099.

## Sessions, recovery and transfer

The browser exchanges a recently authenticated ID token for a host-only HttpOnly SameSite=Lax Firebase session cookie. HTTPS uses Secure and the __Host- prefix. The API verifies the cookie, including revocation, and checks the current account on protected requests. The cookie expires after eight hours. Sign-out clears it across tabs in that browser. Account mutations with cookies and session exchange require a same-origin request and a custom request header. [Firebase session cookies](https://firebase.google.com/docs/auth/admin/manage-cookies) Each protected API request checks Firebase token revocation, the current role and the account's disabled status. Settings reauthenticates with the current password before changing it. Use HTTPS, prevent framing of private portal pages at the gateway, and keep credentials, tokens, action links and message bodies out of logs.

**Invitation replacement.** An expired or consumed invitation offers **Request a new invitation**, addressed to the team contact. A permitted manager uses **Resend invitation** on the pending account. For a pending Owner the designated operator reruns setup. Password setup never grants a role.

**Password recovery for a user who cannot sign in.** For the pilot, use Firebase's password-reset email from the authorized operator console after verifying the request against the existing account. Configure and test a separate recovery template with the Firebase-hosted reset handler. Do not use the invite UI or change a role during recovery. Confirm the old password fails, the replacement works, and the account retains its UID and role. If a credential may be compromised, revoke refresh tokens and inspect recent activity. A self-service recovery form can follow the pilot. [Firebase email action handlers](https://firebase.google.com/docs/auth/custom-email-handler)

**Owner recovery or transfer.** Use password recovery when the approved Owner still controls the mailbox. If the mailbox is lost or the organization approves a successor, require independent approval for the successor's identity. A privileged operator takes the portal API and bootstrap jobs offline, records both UIDs and the current claims, and verifies the successor is an active, password-configured participant. Using the Firebase Admin SDK against the confirmed project, demote or disable the former Owner, preserve unrelated claims, revoke their refresh tokens, and assign the Owner claim to the verified successor. Enumerate accounts and confirm exactly one active Owner before reopening the API. If interrupted, keep the portal offline and complete the transfer or restore the recorded roles. Update the approved Owner email and pilot list and verify both accounts' next protected requests. This procedure stays outside the portal UI.

## Staging acceptance

With the local review stack running, `npm.cmd --prefix staff-service run test:staging-build` builds into a temporary directory, verifies the mock switcher is absent and tests the opt-in Owner dashboard in Chrome. The test redirects Firebase sign-in to the local emulator. It makes no real delivery or hosted account calls.

Verify the private gateway, HTTPS routing and project identity. Send one approved invitation and confirm delivery, sender identity, action-link origin, successful redemption, and denial on reuse and expiry. Verify a separate recovery message, password change, session expiry and revocation. Test sign-out, direct management links, Owner demotion of a signed-in Board Admin, and deactivation of a signed-in user. Test all three Sign links while signed out of Sign. Record results before widening access. Roll back the website by rebuilding without the enable flag and withdrawing the gateway's staff API routes.

For initial Owner setup on the isolated local emulator, an authorized operator can read the approved email's PASSWORD_RESET message from the emulator's operator endpoint and open its code as `http://127.0.0.1:5173/staff#invite={oobCode}`. Keep the action code private. The portal's role-filtered manager outbox does not distribute Owner credentials.


## Hosted Terminal acceptance

Run the existing browser suite with `TEAM_BROWSER_STAGING=1`, the two staging browser origins, the staging tenant ID, the two staging-only Terminal test passwords (`STAGING_TEAM_PASSWORD` and `STAGING_ADMIN_PASSWORD`) and operator ADC for test-user provisioning. It creates and removes fictional tenant users. Run `node --test staff-service/terminal-browser.test.js` from the website checkout. Check verifier and Terminal request logs for distinct instance IDs during repeated redemption and revocation checks before marking multi-instance hosting verified. The successful Firestore emulator test uses separate clients and cannot establish hosted IAM or instance placement.
