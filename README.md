# Solaria Capital

Marketing site for Solaria Capital — a privately held investment firm
operating the Medallion Fund, Solaria Ventures, and Solaria Research.

## Local development

```bash
npm install
npm run dev
```

Open http://localhost:5173.

## Production build

```bash
npm run build
npm run preview
```

## Deploy to Google Cloud Run

The repo ships with a multi-stage `Dockerfile` that runs the Node server on
Cloud Run's `$PORT`.

If you've already connected this GitHub repo to a Cloud Run service via the
Cloud Console (Cloud Run → "Continuously deploy from a repository"), every
push to `main` will:

1. Trigger Cloud Build
2. Build the image from this `Dockerfile`
3. Deploy a new revision to your Cloud Run service

To deploy manually instead:

```bash
gcloud run deploy solaria-vc \
  --source . \
  --region us-central1 \
  --allow-unauthenticated
```

### Local Docker test

```bash
docker build -t solaria-vc .
docker run --rm -p 8080:8080 -e PORT=8080 solaria-vc
# open http://localhost:8080
```

## Tech

- Vite + React 18 + TypeScript
- Tailwind CSS 3
- Node 24 server (`server/index.js`) that:
  - Serves the built static app from `dist/`
  - Proxies `/api/quotes` to Stooq (with Yahoo Finance fallback) for real
    equity + index prices
  - Proxies `/api/crypto` to CoinGecko for BTC/ETH
  - Handles `POST /api/contact` — validates, honeypots, rate-limits,
    and emails the partner inbox via Resend
  - Caches responses in-memory (15–60s TTL)
  - Loads Solaria Sign (`server/sign/`) on the first `/api/sign` request, so
    the other routes still use only built-in Node modules

## Enabling the contact form (one-time, ~2 minutes)

The contact form posts to `POST /api/contact`, which emails
`contact@solariavc.com` via Resend. Delivery requires an API key:

1. Sign up at https://resend.com (free, no domain required).
2. Create an API key (Dashboard → API Keys → Create).
3. **Production (Cloud Run):** Edit & deploy a new revision →
   **Variables & Secrets**, add:
   - `RESEND_API_KEY` = `re_xxxxxxxxxxxx` (required)
   - optional: `CONTACT_FROM_EMAIL` = `Solaria Capital <onboarding@resend.dev>`
   - remove any old `CONTACT_TO_EMAIL` if present (recipient is hardcoded to
     `contact@solariavc.com`)
4. **Local:** copy `.env.example` → `.env`, set `RESEND_API_KEY`, then run
   `npm run server` (and `npm run dev` for the Vite UI; `/api` is proxied).
5. Deploy. Submissions arrive as formatted email with Reply-To set to the
   sender.

Resend's free tier includes 3,000 emails/month and uses
`onboarding@resend.dev` as the sender by default — no domain
verification needed. To send from `@solariavc.com`, verify the domain
in Resend and set `CONTACT_FROM_EMAIL` accordingly.

## Digital business card (`/card`)

`public/card/index.html` is a standalone page — the URL programmed into the
NFC business cards (`https://solariavc.com/card`). It is `noindex` and not
linked from the site.

- **Save contact** links to `/card/johnson-jiang.vcf`, a real `text/vcard`
  response generated by `server/index.js`. iOS Safari opens its native
  "Create New Contact" sheet straight from the tap; Android and desktop
  download a named `.vcf`. The page appends `?saved=YYYY-MM-DD` (the
  recipient's local date) so the contact note says "Saved on" without
  assuming an in-person meeting. Legacy `?met=YYYY-MM-DD` links still work;
  `saved` takes priority when both parameters are present. Missing or invalid
  dates fall back to the current date in `America/Los_Angeles`.
  The saved contact contains no photo.
- **Send me yours** posts to `POST /api/contact` with `kind: "card"` (plus an
  optional `phone`). Card submissions are emailed to
  `JohnsonJiang@solariavc.com` directly (the site's contact form still goes
  to `contact@solariavc.com`). Needs `RESEND_API_KEY` like the contact form.
- **Share** uses the Web Share API where available, otherwise copies the link.
- `public/card/og.png` (1200×630) is the link preview shown when the card URL
  is texted or posted.

In development, run `npm run server` alongside `npm run dev`; Vite proxies
both `/api` and the `.vcf` route to it. Open the page directly at
`http://localhost:5173/card/index.html`.

## Staff page (`/staff`)

`staff.html` (`src/staff/`) collects the team's links: Solaria Sign (documents,
`/sign/verify`, Team), Solaria Terminal (https://terminal.solariavc.com and its
`/admin`), the business card pages and vCards, Titan webmail, the contact inbox
and the public pages. The only way in is "Staff login" at the very bottom of the
site's footer. It has no sign-in of its own, since each tool signs people in
itself, and it is served with `noindex` and kept out of `robots.txt`. Add a link
by editing `tools` in `src/staff/Staff.tsx`.

## Solaria Sign (`/sign`)

Solaria's own electronic signing, at `https://solariavc.com/sign`. Upload a PDF,
place fields, and send it by email or with a link. Each signer agrees to the
electronic records disclosure, signs, and receives a sealed copy with its
certificate of completion. `/s` is the signer's page and `/sign/verify` checks a
file against our records.

The address in `OWNERS` (`server/sign/config.js`) signs in at `/sign` and can add
and remove admins on the Team page. Admins can send documents and see everything
the firm has sent, and removing one ends their access at once. Nobody else can
sign in.

To send the same document to many people (onboarding, say), leave one signer's
name and email blank, place their fields, then choose **Review and send → Send to
a list** and paste one person per line (`Name, email`, a spreadsheet column pair,
or `"Name" <email>`). Each person gets their own copy with its own audit trail and
sealed PDF; anyone else on the draft, such as a countersigner, is on every copy.
Up to 50 people per batch. The draft stays, so it can be reused for the next group.

A list send shows as one row that opens to show each person. Tick documents (or a
whole group with the checkbox on its heading) to remind, void, move or delete them
together. **Remind** emails each signer whose turn it is, skipping you and anyone
you share a link with yourself.

When documents are waiting for your own signature, the documents page offers
**Sign all**. You see each distinct file, agree to electronic records, adopt your
signature once, and sign every copy of that file in one go; a different file is
shown before it can be signed. Each copy still gets its own viewed, agreed and
signed entries in its audit trail, marked as signed from the documents page. A
document with text or checkbox fields only you can fill in has to be signed from
its email.

Anyone sent a document can see all of theirs at `/sign/my`: they enter their
address, get a one-time link (sent only if that address has documents), and see
what is waiting for them, what they have signed, and what is complete, with a
button to sign or download each. Every signing email links there.

In the editor, **Find fields automatically** reads the PDF for signature lines
(`Signature: ____`, `Date: ____`, `Print Name: ____`, `Initials:` and the like)
and places matching fields for the selected signer to check. Fields can also be
dragged from the palette onto the page.

Documents can be sorted into folders, and the list can be searched by title,
name or email. Deleting anything, drafts included, moves it to the Deleted
folder (always shown beside the folders), with Undo right after; it can be
restored from there, and signers keep their links. From there the owner can delete it forever, which
erases its files, including older stored versions, its audit trail and its
`/sign/verify` record. Emailed copies stay with the people who received them, and
the bucket's soft delete policy keeps erased files recoverable in Google Cloud for
seven days. The disclosure promises a paper copy of any record on request, so keep
your own copy of anything you erase. A document out for signature has to be voided
first.

### Working on it locally

```bash
npm run server   # API on :8080
npm run dev      # open http://localhost:5173/sign
npm test
```

Data goes to `.sign-data/`. Without `RESEND_API_KEY`, mail is written to
`.sign-data/outbox`, which is where to find sign-in links and signing codes.

### Going live (one time)

Production keeps records in Firestore (`sign_*` collections in the `(default)`
database) and files in a private bucket. Cloud Run's service identity needs no
key file.

```bash
gcloud storage buckets create gs://gen-lang-client-0188652481-solaria-sign \
  --location=europe-west1 --uniform-bucket-level-access --public-access-prevention
gcloud storage buckets update gs://gen-lang-client-0188652481-solaria-sign --versioning
gcloud run services update solariavc --region europe-west1 --memory 1Gi
```

Sealing a 20 MB file peaks near 300 MB, so 512 MiB can't hold two at once.

Then, in this order:

1. Push to `main` and wait for the new revision.
2. If traffic is pinned to an older revision, move it by name, because
   `--to-latest` picks the newest ready revision, which can be a tagged test build:
   `gcloud run services update-traffic solariavc --region europe-west1 --to-revisions <new-revision>=100`
3. Check `status.traffic` with `gcloud run services describe`. Older revisions
   show the marketing site at `/s`, so a signing link sent too early opens the
   wrong page. To add a test tag, use `--update-tags`, because `--set-tags`
   replaces every existing tag.
4. Send yourself a test document. Check that the email arrives, that your own IP
   address is on the certificate, and that Acrobat shows the timestamp as valid.

### Changing the legal text

`server/sign/disclosure.js` holds the words signers agree to. Every consent and
signature records their version and SHA-256, and the certificate prints them, so
follow the note at the top of that file before changing them.

### Documents that don't belong here

E-SIGN (15 U.S.C. § 7003) and California's UETA (Civ. Code § 1633.3) leave these
out, so keep them out of Solaria Sign unless counsel says otherwise:

- Wills, codicils and testamentary trusts
- Adoption, divorce and other family law matters
- Court orders, notices and filings
- Anything governed by the Uniform Commercial Code other than sales and leases,
  including negotiable promissory notes, investment securities and secured
  transactions
- Notices of default, foreclosure or eviction on a primary residence, notices
  cancelling utilities or health or life insurance, product recalls and
  hazardous materials documents
- The specific California transactions listed in § 1633.3(c)
- Anything that must be notarized, because there is no notary step

Have counsel confirm before using it for fund subscription documents.
